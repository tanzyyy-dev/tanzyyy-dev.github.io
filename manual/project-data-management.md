# 作品データ管理スキル 運用マニュアル

このマニュアルは、ポートフォリオの作品データを **AIと対話しながら点検・登録・更新** するための、人間向け手順書です。

## 基本方針

- データはGitHub上のTypeScriptファイルで管理します。DB・CMS・常設の管理画面は使いません。
- AIは毎回、**その時点の型定義** を読んで入力項目を判断します。項目をスキル内に固定しません。
- 作品リポジトリを渡すと、閲覧できるREADMEなどから初期値を提案します。
- **確認・修正しやすい画面** を優先します。利用可能ならチャット内フォーム、そうでなければ編集しやすい項目別の確認表を使います。
- フォームへの回答と、GitHubへの反映は**別の操作**です。反映前に変更内容を確認します。

## どこにある？

| 用途 | パス |
| --- | --- |
| AI用スキル | `.agents/skills/project-data-management/SKILL.md` |
| このマニュアル | `manual/project-data-management.md` |
| 共通・カテゴリ別の型 | `src/data/types.ts` |
| 作品別のゲームデータ | `src/data/projects/games/{slug}.ts` |
| カテゴリ別の登録一覧 | `src/data/projects/{games,contents,tools}/index.ts` |
| 既存ゲームAPI（互換窓口） | `src/data/games.ts` |
| 共通コンテンツ・翻訳 | `src/data/content.ts` |

現在の作品データは `src/data/types.ts` に共通・カテゴリ別型、`src/data/projects/games/{slug}.ts` に作品別データ、`src/data/projects/{games,contents,tools}/index.ts` にカテゴリ別の一覧を置きます。`src/data/games.ts` は既存画面の互換窓口です。contents/toolsはまだ作品登録がないため空の一覧です。ntents.ts` が存在する前提では操作しません。

## 使い方

### 新しい作品を登録する

AIに、例えば次のように依頼します。

\`\`\`text
project-data-management スキルで新規作品を登録したい。

【管理対象のポートフォリオ】
https://github.com/tanzyyy-dev/tanzyyy-dev.github.io

【作品のリポジトリ】
https://github.com/{OWNER}/{REPO}

【作品名（分かれば）】
{作品名}

現在のTypeScript型を読んで、調査できた情報を初期値に入れた
確認・修正しやすいフォームを出して。
今回はmain直pushでよい。反映前に差分を確認させて。
\`\`\`

1. AIが既存の型・登録データを読み、対象リポジトリを調査します。
2. 作品名、URL、ステータス、料金、ログイン条件、対応端末、日英説明、画像、日付、更新履歴など、**実際の型に応じた項目**が表示されます。
3. 初期値を確認し、間違いを直します。「推定」「未確認」の項目は特に注意してください。
4. フォームまたは確認表で回答を返します。
5. AIが差分・検証結果を提示します。内容に問題がなければ「確認した差分を指定の方式で反映して」と承認します。
6. AIが承認された方式（main直push、またはブランチ＋PR）で反映し、チェック結果を報告します。
7. 人間がローカルで画面を確認し、PRの差分とCIを確認したうえで、**別途明示的に承認してmainへマージ**します。

### 既存作品を修正する

\`\`\`text
project-data-management スキルで既存作品を点検・更新したい。

【管理対象のポートフォリオ】
https://github.com/tanzyyy-dev/tanzyyy-dev.github.io

【作品のslugまたは作品名】
{作品slug または 作品名}

【作品リポジトリ（任意）】
https://github.com/{OWNER}/{REPO}

既存値を初期入力した確認フォームを出して。
未変更項目と更新履歴は維持して。反映方法は依頼時の指定に従って。
\`\`\`

既存データを初期値として読み込みます。**変更していない項目は維持**し、変更点だけを確認します。

### 公開状態を変更する

\`\`\`text
project-data-management スキルで作品の状態を変更したい。

【管理対象のポートフォリオ】
https://github.com/tanzyyy-dev/tanzyyy-dev.github.io

【対象作品】
{作品slug または 作品名}

【変更後の状態】
{開発中 / 稼働中 / メンテナンス中 / サービス終了}

変更前後を確認してから、ブランチとPRで反映して。
\`\`\`

終了・停止の際も、原則として既存の状態フィールドを使います。**削除は明示的に依頼したときだけ**行います。

### 作品リポジトリがない場合

\`\`\`text
project-data-management スキルで新規ゲームを登録したい。

【管理対象のポートフォリオ】
https://github.com/tanzyyy-dev/tanzyyy-dev.github.io

【作品名】
{作品名}

作品リポジトリはありません。型に沿って必要項目を入力させて。
反映前に差分を確認させて。反映方法は依頼時の指定に従って。
\`\`\`

リポジトリは必須ではありません。AIは型定義から必要項目を案内します。

## AIによる補完の見方

| 表示 | 意味 | 人間がすること |
| --- | --- | --- |
| 既存データ | 現在のポートフォリオに登録済み | 必要なら修正 |
| リポジトリ確認済み | README、設定ファイル、リリース等で根拠あり | 公開情報と一致するか確認 |
| AIの推定 | 根拠が不十分な提案 | 必ず確認 |
| 未確認 | 情報を取得できなかった | 入力するか、不明として扱う |

特に、**公開URL・初回公開日・最終更新日・公開バージョン・料金・ログイン要件・対応端末**は、ソースコードから確定できないことがあります。AIの提案をそのまま採用せず、公開中の実態と照らしてください。

## フォームについて

目的はHTMLファイルそのものではなく、**人間が見て直しやすく、回答をAIへ返せるUX**です。

- チャットが対話型入力に対応していれば、フォームの値をそのまま会話に送ります。
- 非対応なら、項目ごとに編集できる確認表や段階的な質問に切り替えます。
- 単独のHTMLを作る場合、ブラウザで開くだけでは回答はAIに送信されません。回答のコピー・貼り付けなど、戻す方法を明示して使います。
- フォームの送信だけでGitHubには書き込みません。必ず変更プレビューを確認してください。

## 更新時のチェックポイント

- [ ] 日本語・英語の両方を確認した
- [ ] 公開URL・リポジトリURLを確認した
- [ ] ステータス、料金、ログイン条件、端末対応が実態に合っている
- [ ] 画像と代替テキストが適切で、参照先が存在する
- [ ] 日付・バージョンは裏付けがあり、不明な値を推測で埋めていない
- [ ] 既存の更新履歴・作品ID・URLを意図せず変更していない
- [ ] AIの差分を確認してから反映を承認した
- [ ] ビルド／CI結果を確認した

## よくある困りごと

**リポジトリをAIが読めない**：非公開・権限不足・接続不可の可能性があります。READMEの内容を貼るか、アクセス可能な接続を用意してください。認証情報を会話に貼らないでください。

**型にない項目を追加したい**：まずデータスキーマ変更として相談してください。作品登録作業の途中でAIが勝手に型を増やすことはしません。

**フォームが表示されない**：チャットの入力UIの対応状況によります。項目別の確認表で同じ内容を点検できます。

**誤って登録した**：Gitの履歴から変更を追えます。AIに対象コミットや作品IDを伝え、差分を確認して修正を依頼してください。

## 運用範囲

このスキルは **作品データのメンテナンス** 用です。作品ごとのデータファイルへのリファクタリング、GA4の導入、UIの変更、公開フローの変更はそれぞれ別途相談・承認して進めます。

## 画像・GIFの準備と配置

作品登録フォームで **画像の候補・出典・代替テキスト・掲載許可** を確認したあと、**作業ブランチ上で** 実ファイルを配置します。READMEに画像URLがあるだけでは、勝手に流用可能とは判断しません。

1. 作品側でデモGIFやスクリーンショットを用意します。公開可能な画像か、ライセンス・個人情報・機密情報を確認します。
2. AIに画像ファイルを添付するか、ローカルの作業ブランチにコピーします。既存のゲームは `public/images/games/hollywood-hacker-demo.gif` のように配置しています。新規作品では重複しない `public/images/games/{slug}-demo.gif` 等を候補にします。実際の形式はPNG/WebP等でも構いません。
3. AIは **実際に存在する画像** に合わせてデータの `media[].src` を `/images/games/{ファイル名}` のように設定します。画像が未完成なら、スキーマで許されるプレースホルダーを利用し、未配置ファイルを参照しません。
4. 画像とデータを同じブランチにコミットし、PRの変更ファイルに両方含まれることを確認します。
5. ローカルで日英ページ、画像の表示、縦横比、GIF再生、スマホ幅、代替テキストを点検します。容量が大きいGIFは最適化を検討します。

**画像の準備ができない場合**：登録を保留するか、明示的に仮画像扱いで進めるかを人間が決めます。AIが存在しない画像や未確認の外部素材を捏造しないこと。

## 反映方式・ローカル確認の標準フロー

```text
main
 └─ docs/project-data-workflow または data/{slug}-{operation}
      ├─ データ編集 + 画像配置
      ├─ 型チェック・ビルド
      └─ Pull Request → ローカル確認 → 人間の承認 → mainへマージ
```

1. AIは管理対象リポジトリを確認し、ユーザー指定の反映方式を採用します。現在はmain直pushも許可します。PR方式を指定された場合だけmainから作業ブランチを作成します。**作品リポジトリは情報取得元であり、書き込み対象ではありません。**
2. AIは差分を見せ、ユーザーが承認した内容だけを指定ブランチへ反映します。PR方式ならPRを作ります。PRには作品名、変更点、画像の有無、未確認事項、検証結果を記載します。
3. 手元で `git fetch origin`、`git switch {作業ブランチ名}`（未作成の場合は `git switch -c {作業ブランチ名} --track origin/{作業ブランチ名}`）し、`npm ci`、`npm run dev` でローカル確認します。必要に応じて `npm run build` も実行します。
4. 日本語・英語のページ、作品カード・詳細、画像、リンク、ステータス表示を確認します。問題があればPRブランチに修正を追加します。
5. PR方式ならGitHub Actionsと差分を確認してから人間がマージします。main直pushなら反映後のCI結果を確認します。AIにマージを依頼する場合も **PR番号を指定して明示的に許可** してください。

※ GitHubのブランチ保護・必須レビュー・必須CIの設定は、このマニュアルを追加しただけでは有効になりません。必要なら別途GitHub側で設定します。

## データファイルの追加ルール

1. `src/data/types.ts` から現在のカテゴリ型を確認します。共通項目は `ProjectBase`、カテゴリ固有項目は `Game` / `Tool` / `Content` に定義します。
2. `src/data/projects/{カテゴリ}/{slug}.ts` に1作品1ファイルで追加します。
3. 同じカテゴリの `index.ts` にimportと一覧への登録を追加します。登録漏れやslug重複を確認します。
4. `contents` と `tools` はまだ実作品がないため、最初の登録時に表示仕様と固有項目を確認してから実装します。型だけで表示画面が完成したことにはなりません。
5. 現行の画面が使う `src/data/games.ts` のAPIは維持します。

### 反映方法の指定

現在は**main直push可**です。ユーザーがPR方式を指定した場合に限り、作業ブランチ・PR・レビュー・マージを使用します。どちらもデータ確認フォームの送信だけでは書き込みません。明示的な反映承認が必要です。
